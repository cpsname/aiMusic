## 0. 这份文档解决什么

平台代码**零产品分支**:平台不知道「星缘」是什么,也不知道有几位咨询师。
它只提供三样机制 —— 人设的分段组合、平台事实变量的注入、嗓音的选定。
产品负责提供内容,并自持目录。

本文档写清这条边界上的**每一个接口点**:产品要往哪里放什么、平台会回什么、
以及各自的失败形态。

**不在本文档范围**:产品仓内部实现(表结构、端点路由、鉴权)——
那是产品仓自己的设计,平台不做规定。

## 1. 三轴模型

咨询师 = 三段人设在运行时拼接。**顺序固定,且是安全项**。

| 段 | 内容 | 决定期 | 产权 | 载体 |
|---|---|---|---|---|
| **A 专业域** | 会做什么:调哪些工具、产出什么结构 | 发布期 | 平台机制 + 产品内容 | `pt_prompt_templates` · `template_type=system_prompt` |
| **B 个性** | 怎么开口:语气、句长、称呼、情绪基调 | 发布期 | **产品** | `template_type=persona_style` |
| **C 地区** | 对谁说:语言、当地时刻、文化语境、合规声明 | **运行期** | **产品** | `template_type=persona_region` |

拼接顺序 **A → B → C**:

- B 可以调整**说法**,不能扩大 A 定的**能力边界**;
- C 放最后,因为**合规声明必须能覆盖前两段**的表达。

顺序反过来不是排版问题,是越权。平台侧有单测钉住顺序。

**模板总数 = 6 + 6 + 3 = 15 段**(6 专业域 + 6 个性 + `zh`/`en`/全球默认),
而不是 6 × 6 × 2 = 72 份。中英差异在 B 段**内部**用条件分支处理,
**不为第二种语言复制模板**(见 §3.3)。

### 3.2 模板正文的书写规则

- **模板引擎是 Go `text/template`**,并且开了 `missingkey=error`。
  这意味着:模板里引用了 `{{ .foo }}` 而 `foo` 没被注入,**整段渲染失败**,不是留空。
  凡引用的变量必须 ① 在 `variable_schema` 里声明 default,或 ② 由平台注入(见 §4)。
- **白名单函数与参数序**(2026-08-22 逐条实测钉死)。
  ⚠️ **写错参数序不会报错,会静默输出错值** —— 与 §3.3 那个 `__locale` 缺陷同类。

  | 函数 | 签名 | 正确写法 | 管道写法 |
  |---|---|---|---|
  | `upper` `lower` `trim` | `(s)` | `{{ upper .x }}` | ✅ `{{ .x \| upper }}` |
  | `trimPrefix` | `(s, prefix)` | `{{ trimPrefix .x "zh-" }}` | 🔴 **不可用** |
  | `trimSuffix` | `(s, suffix)` | `{{ trimSuffix .x "-CN" }}` | 🔴 **不可用** |
  | `replace` | `(old, new, s)` | `{{ replace "-" "_" .x }}` | ✅ `{{ .x \| replace "-" "_" }}` |
  | `join` | `(items, sep)` | `{{ join .list ", " }}` | 🔴 **不可用** |
  | `default` | `(fallback, value)` | `{{ default "English" .x }}` | ✅ `{{ .x \| default "English" }}` |
  | `dateFormat` | `(layout, in)` | `{{ dateFormat "2006-01-02" .d }}` | ✅ `{{ .d \| dateFormat "2006-01-02" }}` |
  | `printf` | `(format, args…)` | `{{ printf "%s-%s" .a .b }}` | — |
  | `now` | `()` | `{{ now }}` | — |

  🔴 **「管道写法不可用」的含义是静默出错,不是报错**:`{{ .x \| trimPrefix "zh-" }}`
  会被求值成 `TrimPrefix("zh-", .x)`,输出 `"zh-"`。渲染成功、非空、看起来像个值。
  管道把左侧塞到**最后一个**参数位,只有最后一位是待处理数据的函数才安全。

  ⚠️ **`now` 是服务器时间(UTC),不是用户当地时刻** —— 当地时刻用 `__local_time`(§4)。
  ⚠️ `default` **救不了缺键**:`missingkey=error` 在求值时就已报错,轮不到它兜底。
    但它救得了**空串**(平台注入的变量恒存在、未知时为空串),故
    `{{ default "English" .__language_name }}` 是有效的兜底写法。
- 条件与比较用内置 `if` / `eq` / `ne` / `and` / `or`。

### 3.3 B 段(个性):中英差异写在同一份模板里

```
{{ if eq .__language "zh" }}
你是塔罗师星语。语气温和,句子短,多用意象...
{{ else }}
You are Xingyu, a tarot reader. Speak in short, warm sentences...
Respond in {{ default "English" .__language_name }}.
{{ end }}
```

**不要为英文另建一份模板。** 一位咨询师 = 一份 B 段模板,内部分支。

> 🔴 **2026-08-22 勘误:此前本示例写的是 `{{ if eq .__locale "en" }}`,那是错的。**
>
> `__locale` 是**完整的** BCP-47 标签(§4),客户端发的是 `en-US` / `en-GB` 而不是裸 `en` ——
> 于是 `eq .__locale "en"` 对**几乎全部真实流量**都为假,英文用户落进 `else` 拿到中文人设。
> 而它**不报错**:解析通过、渲染通过、输出非空。生产实查该缺陷尚未进库(零份模板引用
> `__locale`),但照抄示例的下一个人必然踩中。
>
> 修法不是把 `"en"` 改成枚举 `en-US`/`en-GB`/…,而是用 §4 新增的 **`__language`**
> (归一后的主子标签 `zh` / `en` / `pt`)—— 一次 `eq` 解决,且不会随新市场增加而失效。
>
> **判据方向也建议反过来写**(判「是不是中文」而不是「是不是英文」):未知语言
> (`__language` 为空串)一律落进非中文分支,再由 `__language_name` 指定实际语言。
> 正向判断会让每个新语言在被显式枚举之前都掉进中文分支 —— 而那个分支不会报错。
>
> 简繁之分同理:用 `__script`(`Hans` / `Hant`)而不是枚举 `zh-CN`/`zh-TW`/`zh-HK`。

B 段只写「怎么说」:语气、句长、称呼方式、口头习惯、情绪基调。
**不写「会什么」** —— 那在 A 段。越界会破坏能力边界,且 A 段变更时你的 B 段会与之冲突。

### 3.4 C 段(地区):三份

首轮落**语言圈层**,精确地区层留空:

| 解析键 | 用途 |
|---|---|
| `zh` | 中文市场 |
| `en` | **覆盖 US / GB / AU / CA / SG 等全部英语市场**,不必逐国写 |
| 全球默认 | 回落终点。**必须先有** —— 缺它则回落链断,渲染会拿不到 C 段 |

回落链:**精确地区 → 语言圈 → 全球默认**。
等某个具体市场出现特殊合规要求时,再加一行精确地区档案即可,机制天然支持。

C 段内容:称谓习惯、禁忌话题、节日语境、**法定声明**。
英语市场普遍要求「仅供娱乐」类声明 —— 这是 C 段存在的核心理由之一,
也是它必须排在最后一段(能覆盖前两段表达)的原因。

### 3.6 A 段(专业域):同一份模板怎么同时服务打字和打电话

{{ if eq .__modality "voice" }}

{{- else }}
…文字口径…

#### 改 A 段的流程

> ⚠️ **工具链已退役(2026-08-28 用户裁决)**:`cmd/tools/persona_domain_seed`
> 与其输入 `docs/migrations/seed/divination_domain/` 均已删除且历史重置不可恢复。

原工具的四道对账(现为人工核对规格):

| # | 对账 | 拦住什么 |
|---|---|---|

Agent 读的是 `persona.system_prompt_ref.version_pin`,那是一个确切的版本 bid。

2026-07-29 有人给六份 A 段各发了一版加强 emoji 的新版本,live 指针推了,
**pin 没动** —— 那一版从此没被任何一次对话读到过,躺了 25 天。

生成的迁移把「发版本」与「重新 pin」绑在同一个事务里,并有后置断言:
六个 Agent 的 `version_pin` 必须等于各自 A 段模板的 `live_version_id`,否则 `RAISE`。

## 4. 契约 B — 平台注入的事实变量

> 就绪度:**已交付**。清单已冻结,可直接在模板里引用。

平台从请求 header 归一后注入,**零文化判断**。全部带 `__` 前缀 ——
这个前缀的语义是「平台注入、模板不可伪造」,业务变量无法覆盖同名键。

| 变量 | 示例 | 说明 |
|---|---|---|
| `__locale` | `zh-Hans` · `pt-BR` | 归一后的**完整** BCP-47。⚠️ 不要拿它做语言判断 —— `en-US` ≠ `en`,见 §3.3 勘误 |
| `__language` | `zh` · `en` · `pt` | **语言主子标签**(ISO 639-1)。做语言分支**用这个**,一次 `eq` 即可 |
| `__script` | `Hans` · `Hant` · `Latn` | 书写系统(ISO 15924)。简繁分支用它,不要枚举 `zh-CN`/`zh-TW`/`zh-HK`。⚠️ 未显式声明时按 CLDR 补全(`zh`→`Hans`),是标准规则而非用户明说的事实 |
| `__region_source` | `store` · `timezone` | 地区判定命中了回落链的哪一级。**给排障用,不是给模型看的** —— 出现「合规声明发错市场」时,没有它无从判断是判定错了还是数据配错了 |
| `__language_name` | `Simplified Chinese` · `American English` · `Brazilian Portuguese` | **让模型用什么语言说话的唯一手段** —— 原生音频模型不接受 `languageCode`,只能写进提示词。⚠️ 2026-08-22 勘误:此前本行举例为 `简体中文` · `Português`,**是错的** —— 返回的是**英文名**(`Locale.LanguageName()`),不是语言自称。照旧例写 `eq .__language_name "简体中文"` 会永不匹配。另注意它带地区修饰(`American English` 而非 `English`),**不要拿它做相等判断** —— 判语言用 `__language` |
| `__region` | `CN` · `BR` | ISO 3166-1 alpha-2,C 段的解析键 |
| `__timezone` | `Asia/Shanghai` | IANA。非法值由平台回落,不会原样透传 |
| `__local_time` | `23:14` | 见下方 ⚠️ |
| `__local_date` | `2026-08-21` | 节气 / 星座日期边界 / 节日判断的输入 |
| `__weekday` | `星期四` | — |
| `__day_part` | `night` | 闭集:`morning` `afternoon` `evening` `night` |
| `__utc_offset` | `+08:00` | **占星与合盘真的依赖它** —— 星盘要按准确的当地时刻算 |
| `__conversation_bid` | uuid | 会话维度 |
| `__modality` | `text` · `voice` | **本次是打字还是打电话。**闭集,只有这两个值。同一份 A 段在两个面上有四处互相冲突的要求(输出协议 / emoji / 工具 / 首条上下文),分支写法见 §3.6 |

🔴 **平台维度只有 `conversation_bid`。没有 `agent_id` / `end_user_id` / `tenant_id`。**

前一版列过这三个内部数值 ID —— 那是**错的**,2026-08-21 已移除。
保留变量会进系统提示词,而系统提示词的内容会被模型**转述给用户**,
语音面更是直接朗读。这比 API 泄漏更危险:API 至少是结构化、可审计、能加守卫的;
模型是自由发挥的,没有任何一层能拦住它把一个租户 ID 念出来。

平台侧已加不变量:**保留变量的值一律为字符串**(比逐个点名键名更难绕过),
另有反向断言防这三个键回潮。

**同一条原则适用于产品仓的端点:对外面一律 bid,不出内部数值 ID。**

### ⚠️ 语音会话里 `__local_time` 会过期

Live 的 setup 帧在**建连时一次性下发,之后不可改**,而通话最长 45 分钟。
平台注入的是**会话开始时刻**。

**模板措辞必须写成**「本次通话开始于当地时间 {{ .__local_time }}」,
**不要写**「现在是 {{ .__local_time }}」—— 否则模型会在第 40 分钟说错时间。
这条代码拦不住,只能靠模板规范。

## 5.5 契约 C′ — 开场白

> 就绪度:**已交付**(P-10)。

`persona.greeting` 是**双面**契约(2026-08-23 起):同一段文本,语音面播报、文字面直显。

**语音面**:经 `ready` 事件下发,由**客户端播报** —— 服务端不让模型说第一句。

| 项 | 约定 |
|---|---|
| 位置 | `ready` 事件顶层,**与 `params` 并列**(params 里全是数值阈值) |
| 渲染 | 与人设**同源变量** —— 可用 L1 事实做时段问候或多语言分支 |
| 纯文本 | 不含 `{{ }}` 时恒等下发,零风险 |
| 渲染失败 | **省略字段**,不下发半渲染的原文 |
| 缺字段 | 客户端不播报。这是正常情况,不是错误 |

**文字面**(星缘体验批 2026-08-23):`POST /v1/conversations` 绑定 Agent 建会话时,
开场白在**同一事务内物化为首条 assistant 消息**(`run_id=0`,零上游 token)——
客户端拉消息列表即见,**零客户端改动**。要点:

| 项 | 约定 |
|---|---|
| 渲染时机 | 建会话时**一次性**定格 —— 历史即事实,次日回看仍是当时那句(时段问候不穿越) |
| 时区/语言来源 | 请求头 `X-Language` / `X-Timezone` / `X-Region` / `Accept-Language`(与语音面同一组头、同一条判定链);老客户端不发 → 时段分支走兜底文案 |
| `__modality` | 文字面渲染时为 `text`,语音面为 `voice` —— 模板可分面措辞 |
| 渲染失败 / 缺字段 | **不落消息、不阻断建会话** —— 与语音面「省略字段」同纪律 |
| LLM 上下文 | 开场白作为 assistant 历史进入后续对话上下文 —— 模型知道自己已问候,不会二次自我介绍 |
| 存量会话 | 不回填 —— 历史里没发生过的问候不该被编造出来 |

六位咨询师的开场白正文(时段问候 + 情绪接住 + 信仰锚 + 行动引导;2026-08-23 起
含 `__language` en 分支)的唯一事实源是**最新**的 `*_divination_greeting_*` 迁移
(当前 `20260823h_divination_greeting_en.sql`);可渲染性由
`tests/archtest/divination_greeting_render_test.go` 自动锚定最新迁移,
按时段 × 语言全矩阵渲染守卫(en 变体禁含中文、zh 变体必含中文)。

⚠️ 与人设 A 段**刻意相反**:A 段渲染失败会退化到原文(有总比没有好),
开场白失败则丢弃 —— 它会被**朗读**,一段带着 `{{ }}` 的模板原文念给用户听比不念更糟。

写开场白时因此有一条纪律:**能用纯文本就用纯文本**。要做时段问候或中英分支时才引入占位符,
且引用的变量必须在 §4 的 L1 清单内 —— 引用清单外的变量会让整句被丢弃。

## 5.6 契约 C″ — 语音会话能力(`live` 段)

> 就绪度:**已交付**(P-11)。

Agent 定义顶层的 `live` 段,承载语音会话的**能力**配置。

```json
{
  "live": { "web_search": true }
}
```

### 与 `persona.speech` 的分工

| 段 | 回答什么 | 例 |
|---|---|---|
| `persona.speech` | 这个人的**声音**是什么样 | `voice` |
| `live` | 这个会话**能做什么** | `web_search` |

两者产权方相同(都归产品),但变更节奏不同:嗓音定下来基本不动,能力开关会随
产品迭代反复调整。分开也让将来的语音配置(VAD 灵敏度、上下文压缩阈值)有地方落。

### `web_search` — 联网检索

**这是把「回答要有时效信息」从提示词软约束变成结构性能力的唯一手段。**
在 B 段里写「你可以查最新消息」是没用的 —— 模型没有这个能力。

- **上游自执行**:模型自己完成检索并把结果并入回答。平台零执行负担、零回传链路,
  也不额外计费(检索成本包含在上游的 token 计价里)。
- **不接受分发覆盖**:能不能联网是产品对这个咨询师的设定,不是运营调参 ——
  与价格、模型选型同属那一类。写在 Agent 定义里,改它要重新发布。
- 坏的 `live` 段(不是对象 / `web_search` 不是布尔)表现为**该能力不开**,
  且不连累人设解析。

#### 🔴 占卜六位:不开(2026-08-23 裁决)

塔罗的牌面来自 `seeded_draw`、星盘来自 `ephemeris_chart` —— 事实源是牌与星历,
不是实时网页。开了会让模型把检索到的网页内容当依据讲,稀释专业性,并拉长首答延迟。

**落地形态:definition 里不写 `live` 段。**

这不是"忘了写",是这个字段的正确用法。三条理由,每条都可复核:

| # | 事实 | 出处 |
|---|---|---|
| ① | 缺 `live` 段与 `web_search: false` **运行期完全等价** | `live_session_service.go` 的 `liveToolsOf` —— 前者 map 为 nil 直接返回,后者 bool 为 false 不追加工具 |
| ② | `false` **无法稳定存活** | `agent_definition.go` 的 `WebSearch` 字段带 `json:"web_search,omitempty"` —— `omitempty` + `bool` 意味着 `false` 序列化时被丢掉 |
| ③ | 它今天能留在库里是**偶然** | 写路径全都拷贝原始 map(`DeepCopyDefinition` marshal 的是 map 不是 struct);唯一会抹掉它的 `AgentDefinition.ToMap()` 当前**零生产调用方**。哪天有人把某条写路径接过去,它就静默消失 —— 而因为 ① 的等价性,**什么都不会坏,也没有任何人会发现** |

一个能无症状蒸发的记录不是记录。`web_search` 是能力开关不是三态,
`omitempty` 是对的 —— **显式写 `false` 是在为「行为」设计的字段里塞「决定」**。

决定归文档(即本节),`release_notes` 归变更 —— 将来真要开的时候,
那一版的 `release_notes` 会自然记下为什么改。

> 生产实查(2026-08-23):全库**零个** Agent 带 `live` 段。这里说的不是六位的例外,
> 是当前的普遍状态。

### ⚠️ 函数调用类工具尚不可用

平台的中立层已支持函数声明,但**本段不提供开关**,因为语音会话的工具
**执行链**(执行 / 超时 / 错误归一 / 计费)还没有。现状是:上游发起函数调用时,
平台安全应答「该工具不可用」。

**不要试图绕过这条**去声明函数 —— 声明一个执行不了的工具比不声明更糟:
模型会陷入「调用—失败—重试」,而在用户听来那像是它在犯傻。

## 7. 契约 E — 会话接入

### 7.1 分发身份:客户端只传 code,内部 ID 由服务端解析

**客户端从不传、也不需要知道 `app_id`。** 它只传分发码与签名:

| Header | 值 |
|---|---|
| `X-Distribution-Code` | `com.magiccontent.xingyuan` |
| `X-Timestamp` / `X-Nonce` / `X-App-Signature` | 见 [`overview.md` §5](overview.md) |

平台侧由 `AppSignatureMiddleware` 用 `distribution_code` **单表查出**分发信息,
把 `app_id` / `distribution_id` / `bundle_id` 注入 context;
handler 一律经 `middleware.GetAppID(ctx)` 取用。

🔴 **平台红线:严禁从请求体读 `app_id` / `tenant_id` / `distribution_code`** ——
客户端可伪造,后果是跨租户 / 跨分发计费。

#### 前一版此处列了 `app_id` 数值,那是错的

不是"标清环境"就能补救 —— **这个数值本就不该出现在契约里**。
`app_id` 是平台库 `iap_apps` 的主键,是**内部标识**;它在 dev 与 prod 恰好还是反的
(dev `10=xingyuan`,prod `11=xingyuan`),照抄会在 dev 上打到 Muse 的钱包,
而两个 app 都存在都 enabled,**不会有任何一层报错**。

但那只是症状。根因是我把一个内部 ID 写进了跨仓契约 —— 与 §4 移除
`__tenant_id` 是同一条原则的两次触犯。

#### 产品仓该用什么作 App 维度

**用 `distribution_code`,不要引 `app_id`。**

| | |
|---|---|
| 为什么不引 | `app_id` 是平台库主键,产品库引用它等于跨库外键 —— 与「跨库不建 FK」同一条纪律 |
| 为什么 code 可靠 | 分发码**发版即冻结**,是稳定的业务标识;而内部主键在不同环境可以不同(已被这次踩中) |
| 从哪拿 | 产品服务验签时本来就持有 `X-Distribution-Code`,零额外查询 |

⚠️ **产品仓当前缺的是「验签后解析出 App 维度」这一环。**
`pkg/aigcsign` 只提供签名计算(`Sign` / `Canonical` / `Verify`),
不含 `distribution_code → app_id` 的解析 —— 那需要查平台库的 `iap_app_distributions`。

三条路各自的代价:

| 方案 | 代价 |
|---|---|
| 产品库自存一份 distribution → app 映射 | 数据重复,会与平台漂移 |
| 调平台 API 解析 | 在每个请求上引入常驻服务间调用 |
| **直接用 `distribution_code` 作维度键** | **无** —— 推荐 |

第三条之所以无代价,是因为产品域本就不需要 `app_id`:它要区分的是「哪个产品的请求」,
而 `distribution_code` 恰好就是这个答案,且它已经在手里。

#### 待办 X-0

2026-08-20 的语音通话遥测显示 `distribution_code = tool.genai.generator`(老 GenAI 分发)。
**继续这样打的后果**:钱包作用域、kill switch、分发级参数覆盖**全部落在别的 App 上**。
客户端切到 `com.magiccontent.xingyuan` 即可,不依赖任何平台改动。

### 7.2 会话与风格

- **换风格 = 新开会话**(已拍板)。不做会话内切换 ——
  Live 的 setup 帧建连后不可改,会话内切实际是悄悄重连,那是产品决策不是技术决策。
- **客户端只传不透明 ref,永远不传正文。** 传正文 = 一条直通系统提示词的注入通道。

#### 运行期入参通道(P-14,2026-08-22 交付)

`POST /v1/conversations` 新增可选入参 **`persona_style_bid`**,值是 Prompt BC 的
`pt_prompt_templates.bid`(`template_type=persona_style`)。缺省 = 沿用 Agent 自身人设,
行为与本项上线前完全一致。

**🔴 B1 裁决:传 template bid,不传 style code。** 客户端提过一个更省事的方案
(传不透明的 `styles[].code`,由平台按 `(agent_bid, style_code)` 自行解析)。否掉的理由是硬的:

| | 传 code | 传 template bid |
|---|---|---|
| 平台如何解析 | code→内容的映射是**产品数据** —— 要么把产品目录搬进平台(撞「咨询师目录不进平台」),要么运行时反向调产品服务(撞 §9 红线) | 直接就是 Prompt BC 的主键,平台自有 |
| **跨段越权能不能挡住** | ❌ 平台手里没有 code 的合法集,**什么都校不了** | ✅ 校 `template_type == persona_style`(`TemplateRef.ExpectType`) |
| 加一个风格的成本 | 若把映射写进 Agent definition,则**每加一个风格要重发一次 Agent** | 平台建一份模板 + 产品存一行,零发版 |

客户端反对传 bid 的两条理由都能消掉,而且都是产品层的一行改动:

- **「多一次网络往返」** —— 只在 bid 不在目录响应里时成立。把 `persona_template_bid`
  从咨询师级**下沉到风格级**(`styles[].template_bid`),同一次目录调用就同时拿到 code 和 bid。
- **「code 逐环境稳定而 bid 不是」** —— 成立,但不适用:客户端**从不硬编码也不持久化**
  这个 bid,它是同一次调用里取到的、逐环境的不透明线上值;`code` 继续用于 UI 渲染、
  埋点、选中态与本地记忆。两个属性都保住。

**两道门,顺序不可换**(建会话期,`CreateConversationHandler.checkPersonaStyle`):

1. 无 `agent_bid` → `40935`。没有咨询师就没有可换说法的对象,也读不到 `style_slot`。
2. Agent 未声明 `persona.style_slot` → **`40938`**。放在校验 ref 之前 —— 此时 ref 合不合法
   都不改变结论,早拒省掉一次 Prompt BC 往返。
3. ref 不可用(不存在 / 已归档 / 无已发布版本 / 类型不是 `persona_style`)→ **`40433`**。
   四种成因合并成一个对外码:客户端的补救动作相同(清本地已选风格 → 重拉目录 →
   用默认风格重试),分开只会让端上多写三个分支做同一件事。具体成因留在服务端错误链里,
   只进 slog。

**门在入口 fail-close、热路径 fail-open** —— 这对不对称是刻意的:

| 时机 | 行为 | 为什么 |
|---|---|---|
| 建会话 | **拒绝** | 静默吞掉正是本能力要解决的问题(用户以为换了风格而对话没变),只是换个位置重演。建会话是唯一能当场告诉调用方的时机 |
| Run / 建连 | **跳过 B 段 + WARN** | Agent 发新版撤掉 `style_slot` 时,存量会话应当退回无风格,而不是集体报错 |

**会话级不可变。** 不提供改风格的 PATCH,不可变性由**写面缺席**保证 ——
`EntConversationRepository.Update` 的 SET 列表里没有这一列,于是没有任何代码路径能改它
(源码级守卫 `conversation_persona_style_immutable_test.go` 钉住)。靠 if 校验的话,
只要有人新写一个 handler 就会漏。

**只存 template_bid,不冻结版本。** 风格内容的修订(错字、语气微调)应当惠及既有会话,
与 A 段每次 Run 重新解析 `latest` 同口径。会话定格的是**选了哪个风格**,不是它的某一次
内容修订 —— 冻结会让线上会话永远停在带 bug 的那一版。

**`GET /v1/conversations/:bid` 回显 `persona_style_bid`(只读)。** 客户端从历史列表重进
会话时,只靠本地存会漂移(换设备 / 清缓存),而"当前会话用的哪个风格"要显示给用户。

**语音链路自动在范围内,无需单独设计。** 实时语音面是 `GET /v1/live/sessions/:bid/stream`,
其中 `:bid` **就是 conversation_bid**(与文字对话共用同一套会话身份),人设解析走同一个
`resolvePersona`。风格落在会话行上,语音面随之生效。
(客户端此前引的 `POST /v1/live-sessions` 是 capability BC 的旧令牌签发面,不是这条链路。)

⚠️ **生效前置:六个占卜 Agent 目前一个都没声明 `persona.style_slot`**(2026-08-22 生产实查)。
按上表,此时传风格会被 `40938` 拒绝。开闸需要给它们补 `style_slot` 声明并重发一次 ——
这是**数据动作**,但要走 catalog 发布门禁,不能直写 definition。

### 7.3 Header

| Header | 状态 | 说明 |
|---|---|---|
| `X-Language` | 已有 | 设备语言,如 `zh-CN` |
| `X-Timezone` | 已有 | IANA,如 `Asia/Shanghai`。⚠️ 2026-08-23 真机实测 iOS 端发的是缩写 `CST` —— 平台已做**受控消歧兼容**(`internal/shared/locale/timezone_abbrev.go`:唯一含义缩写直接归一;`CST/EST/PST/IST` 等歧义缩写**必须**有 `X-Region`(或商店地区)佐证才归一,无佐证按未知处理走兜底文案)。客户端仍应尽快改发 IANA 名(Flutter 可用 `flutter_timezone` 取)—— 缩写永远只是降级兼容,新缩写不保证入表 |
| `X-Region` | **P-6 新增** | ISO 3166-1 alpha-2。**需要客户端配合补发** |

地区判定按可靠性五级回落:

```
X-Region  >  IAP storefront  >  X-Timezone  >  X-Language 的地区变体  >  平台默认
```

⚠️ `X-Language` 排最后是因为 `zh-CN` 的 `-CN` 是**语言的书写变体,不是用户所在地** ——
在美国的中文用户设备也是 `zh-CN`。

## 9. 红线

| 一旦出现 | 判定 | 为什么 |
|---|---|---|
| 平台代码里出现 `xingyuan` / 咨询师名 / 地区文化判断 | ⛔ | 产品身份是数据四元组,平台零产品分支 |
| 咨询师目录或地区档案塞进 `acfg_configs` | ⛔ | 2026-08-17 已拍板 |
| 为地区档案 / 风格新建平台表 | ⛔ 先过 `/table-gate` | 与 persona 模板结构同构,几乎必然命中机制家族;豁免不可自签 |
| 平台运行时反向调用产品服务取文案 | ⛔ | D1 定的是**产品 → 平台**单向;反向会在建连热路径引入常驻服务间依赖 |
| 客户端传风格 / 地区**正文** | ⛔ | 直通系统提示词的注入通道 |
| 契约 / 代码 / 迁移里出现 `app_id` 等内部数值 ID | ⛔ | 内部标识不进对外面。它们在不同环境可以不同(dev/prod 的 `app_id` 正好是反的),照抄会**静默打错 App** —— 用 `distribution_code`,见 §7.1 |
| C 段缺失时渲染成空串 | ⛔ | 提示词会出现「本地文化注意事项:」后面空白,模型会自行编造。必须回落全球默认 |
| B 段里写「会什么」 | ⛔ | 那是 A 段。越界会破坏能力边界 |
